# 系统架构与关键流程

这份文档说明简报如何生成、原文获取失败后会尝试什么，以及如何查看处理记录定位问题。使用与配置见 [README](../README.md)，产品目标见 [product.md](product.md)。

## 系统总览

Daily Brief 每天从 Hacker News 收集内容，挑选值得关注的条目，整理成中文简报。整个过程分为五步：

1. **收集候选内容**\
   获取近期发布的内容和热门榜上的内容，合并重复条目，并排除最近已经推荐过的内容。

2. **筛选今天要推荐的条目**\
   结合主题和社区热度，选出最多 5 条技术精选和 2 条圈外热门。部分候选需要先读取原文才能判断主题；对于征集工具、项目或经验的帖子，则需要查看评论中的回答。

3. **读取内容，生成中文摘要**\
   获取入选条目的原文；筛选时已经取得的内容会直接复用。原文获取失败或内容不足时，尝试用 HN 讨论补充，并在摘要中说明来源。具体的获取与回退过程在下一节展开。

4. **保存简报和处理记录**\
   保存供阅读的 Markdown、供网站发布的 JSON，以及候选条目的处理记录。排查“为什么没选中”或“为什么没抓到原文”时，可以查看这些记录。

5. **发布到网站**\
   发布是独立步骤，读取已生成的简报并发送到网站，因此可以单独重试发布，无需重新筛选和生成摘要。

## 原文获取

获取原文时，系统会根据链接类型，选择对应的读取方式：

- **普通网页**：下载页面，提取正文，去除导航、广告等无关内容。系统不会像浏览器一样执行 JavaScript，因此有些网页虽然能手动打开，也可能提取不到正文。
- **GitHub**：仓库链接读取 README；指向具体文件的链接读取该文件。
- **YouTube**：获取视频字幕，作为摘要依据。
- **PDF**：下载文件后提取文字。配置了 Adobe 服务时优先使用 Adobe；未配置或转换失败时，使用本地的 `pypdf`。

取得文字后，系统才会判断这些内容是否足以生成摘要。因此，“没有摘要”可能是没能取得原文，也可能是取得了文字，但内容不足。

以下恢复流程用于已入选的条目。筛选阶段需要读取原文时，只采用较有限的获取方式，不启用 Jina、Wayback 或搜索恢复；已成功取得的正文会在入选后复用。

### 普通网页获取失败后怎么办

对于已经入选的条目，系统会根据失败原因决定下一步。任何一步取得正文后，就停止这条恢复流程。

1. **如果是网络超时，先重试一次。**\
   网站响应慢可能是暂时的，因此再直接请求一次。其他类型的错误不会统一重试。

2. **符合条件时，尝试 Jina Reader。**\
   Jina Reader 是代为读取网页、返回正文的服务。遇到网站的人机验证、提取不到正文、连续网络超时，或缺少证书签发者信息导致的连接失败时，系统会尝试这条路径。普通的 403、404 错误不会自动触发它。

3. **如果原站有人机验证，而且 Jina 也失败，再尝试网页存档。**\
   系统会到 Wayback Machine 查找该页面的历史存档，确认来源与时间符合要求后提取正文。单纯的超时或正文为空，不会走到这一步。

4. **如果这些方式仍未解决原站的人机验证问题，再搜索其他来源。**\
   系统会尝试寻找同一篇文章的其他发布页面；特定情况下，还会寻找 Reuters 的转载或同事件报道。这部分有单独的验证规则，下一段展开。

上述流程适用于普通网页。GitHub 和 YouTube 使用各自的读取方式，失败后不会进入 Jina 和 Wayback 的恢复流程。

### 如何搜索其他来源

原站的人机验证导致获取失败，且 Jina、Wayback 都未能取得正文时，系统会尝试搜索其他来源。搜索使用 Tavily，需要配置 `TAVILY_API_KEY`。

**先找同一篇文章的其他发布页面。**\
系统用文章标题搜索，再实际打开候选页面。页面需要有匹配的标题、明确的转载说明和指向原文的链接，以及可用的正文，才会被接受。仅仅搜索结果看起来相似，并不足以采用。

**如果没找到，再根据原链接决定下一步：**

- **原链接来自 Reuters**：如果此前遇到的是 DataDome 人机验证，并且 Jina 或 Wayback 获取失败，就尝试寻找经过验证的 Reuters 转载。
- **原链接来自其他网站**：尝试寻找 Reuters 对同一事件的报道。采用后，摘要会明确说明依据的是其他报道。

这两条是不同的分支，不会在 Reuters 转载失败后接着搜索同事件报道。

每条搜索路径都有尝试次数限制。找到的页面如果无法获取或未通过验证，就继续检查下一个候选；不会因此启动新一轮搜索。如果最终仍没有可用正文，接下来会尝试 HN 讨论。

### 什么时候使用 HN 讨论

对于普通入选条目，以下两种情况会让系统转向 HN 评论：

- **没有取得原文**：适用的获取和恢复方式都未能提供正文。
- **取得了文字，但不足以写摘要**：例如页面只有登录提示，缺少与文章有关的具体内容。

系统会读取一部分评论，尝试据此生成介绍。如果已经取得部分原文，也会一起提供，并明确区分原文内容和评论中的说法。摘要会标注讨论来源，不把评论当作原文，也不把有限的评论样本当作整个社区的意见。

如果评论获取失败，或内容仍然不足，就保留无法生成可靠摘要的说明，不会继续循环尝试。模型服务报错本身不会触发评论补充。

征集工具、项目或经验的帖子有所不同：这类帖子的主要价值就在回答中，因此在筛选阶段就会读取评论，而不是等原文获取失败后再读取。

## 如何定位原文获取问题

### 第一步：找到当天的条目

打开 `data/YYYY-MM-DD-hn-candidates.json`，按标题、原文链接（`source_url`）或 HN 条目编号（`hn_item_id`）找到对应记录。这些诊断信息保存在候选记录中，网站使用的公开简报 JSON 不包含它们。

先看 `selected`：如果没有入选，查看 `rejection_reason` 了解原因。条目可能在筛选阶段就被排除，因此没有执行后续的获取和恢复流程。

### 第二步：判断问题发生在哪里

按下面几个字段区分情况：

- **`article_retrieval.status` 为 `failed`**：没有取得可用的外部正文，继续查看第三步中的抓取和恢复记录。`not_attempted` 则表示没有尝试抓取，不代表抓取失败。
- **`source_material.status` 为 `insufficient`**：已经取得文字，但模型判断不足以生成摘要，具体原因在同一组字段的 `reason` 中。
- **`summary_generation.status` 为 `failed`**：摘要生成出错，查看同一组字段的 `error_code` 和 `error_message`，定位模型调用或输出处理问题。

这些情况可能先后发生。例如，原文获取失败后，系统仍可能依据评论成功生成摘要。用 `summary_status` 查看最终结果，`summary_basis` 查看摘要依据；不要只凭原文抓取状态判断是否有摘要。

### 第三步：查看对应的尝试记录

**如果是抓取失败**，查看 `article_retrieval` 中的 `method`、`error_code` 和 `error_message`，确认获取方式和具体错误；`fallback_reason` 说明为什么触发了回退。

例如，`method=wayback`、`fallback_reason=cloudflare_challenge` 表示原站遇到 Cloudflare 人机验证，恢复流程已经尝试到 Wayback。此时 `error_code` 解释存档获取为何失败；是否继续搜索其他来源，要看下面的搜索记录。

**如果需要了解搜索恢复**，查看 `article_retrieval` 中对应的记录：

- `same_article_recovery`：寻找同一篇文章，`candidates` 中记录每个候选的结果和原因。
- `syndicated_recovery`：寻找 Reuters 转载，查看 `status`、`error_code` 和 `rejection_reasons`。
- `alternate_reporting_recovery`：寻找同事件报道，查看相同的三个字段。

搜索恢复成功时，`material_origin` 和 `retrieved_url` 记录实际取得的来源，原站失败信息保留在 `origin_failure` 中。

**如果已经转向 HN 讨论**，查看 `discussion_retrieval.status`；获取出错时看其中的 `error_code` 和 `error_message`。原文材料不足的判断仍保存在 `source_material` 中，最终摘要生成结果则看 `summary_generation`。

需要还原完整尝试顺序时，再结合运行日志查看。抓取日志标有 `component=article_fetch`，PDF 提取标有 `component=pdf_extract`，搜索恢复的标记与上面的三个记录名称相同。
