# 系统架构与关键流程

这份文档说明简报如何生成、原文获取失败后会尝试什么，以及如何查看处理记录定位问题。使用与配置见 [README](../README.md)，产品目标见 [product.md](product.md)。

## 系统总览

Daily Brief 每天从 Hacker News 收集内容，挑选值得关注的条目，整理成中文简报。整个过程分为六步：

1. **收集候选内容**\
   获取近期发布的内容和热门榜上的内容，合并重复条目，并排除最近已经推荐过的内容。

2. **筛选今天要推荐的条目**\
   结合主题和社区热度，选出最多 5 条技术精选和 2 条圈外热门。部分候选需要先读取原文才能判断主题；对于征集工具、项目或经验的帖子，则需要查看评论中的回答。

3. **读取材料，生成中文摘要**\
   获取入选条目的网页材料；筛选时已经取得的内容会直接复用。普通入选条目还会取得一份有界的 HN 评论样本，再将可用的网页元信息、网页正文、HN 帖子正文和评论分区交给一次摘要调用。具体的获取与材料组织过程在下一节展开。

4. **比较当天内容并补选**\
   将摘要成功的条目交给模型，比较摘要和有界原文材料；OpenRouter 使用摘要模型，Gemini 使用分类模型。先判断核心信息是否重复，再保留信息更全面、解释更充分且有材料支持的条目；只有质量相当时才以原排名打破平局。同一事件中具有独立信息的文章可以同时保留。确定重复后，从相同栏目的合格候选中按原排名补选，再生成摘要并比较。整次运行最多额外处理 3 个补选候选。

5. **保存简报和处理记录**\
   保存供网站发布的 JSON，以及候选条目的处理记录。排查“为什么没选中”或“为什么没抓到原文”时，可以查看这些记录。

6. **发布到网站**\
   发布是独立步骤，读取已生成的简报并发送到网站，因此可以单独重试发布，无需重新筛选和生成摘要。

## 定时运行与网络暂停

每日 cron 调用 `daily-brief run`，由 `daily_run.py` 在同一个进程中依次生成和发布。日期在开始时固定，模型实例、已收集页面、入选材料和已完成摘要在暂停期间留在内存中。单独的 `generate`、`retry`、`publish` 和模型回放仍只使用各自原有的短重试，不隐式启用长等待。

`network_recovery.py` 为整次定时运行提供共享等待额度：每次十分钟，最多六次，累计等待一小时。HN API、模型服务、发布接口是关键服务，其暂时 DNS 错误、连接中断、超时、HTTP 408 和 5xx 可触发等待，再继续当前操作；不会重跑整份简报。已有短重试仍先执行，模型费用预留和尝试次数不会因长等待重置。证书错误、永久域名解析错误、鉴权、429 额度/限流、无效内容等不触发长等待。429 保留各服务已有的短重试规则。关键服务失败直接沿用该策略，不另外检查网络，也不调用机器的网络修复脚本。

文章网站及 Reader、存档、搜索等材料来源是可替换来源。单站的暂时 DNS 错误、路由错误、超时、连接中断或 HTTP 408/5xx，都不能单独触发全局等待。当前阶段允许的短重试和备用材料均未取得可用正文时，才向 HN 官方 API 的 `/v0/maxitem.json` 发起一次实际 HTTPS 检查。正常返回有效条目编号，或检查遇到非暂时错误，则沿用条目降级；只有检查也遇到暂时网络错误时才申请十分钟等待，再重新尝试当前材料。检查不自带重试，每轮无材料的尝试最多检查一次，socket timeout 为十秒，响应最多读取 64 字节。十秒约束单次 socket 操作，DNS 解析仍受系统解析器超时控制，因此不是整个检查的硬超时。检查位于材料获取预算之外，仅在定时运行的恢复作用域内启用。它确认关键依赖是否也暂时不可用，不诊断整台机器或整个互联网是否断网。

普通入选条目先尝试网页、帖子和评论材料；任何正文分区可用时，交给模型评估充分性，不为缺失的其他分区长等。全部材料不可用时，文章故障需通过上述 HN 检查才可暂停；若本轮已经观察到实际 HN 请求的暂时失败，则直接申请等待，不重复检查。分类所需材料也使用这一区分。每轮网页尝试仍受 120 秒、24 请求预算约束，十分钟暂停在该预算作用域之外；下一轮创建新的有界预算。

六次等待后仍有需要恢复的操作失败，当前生成沿已有条目诊断路径保留可写出的本地结果，`run` 返回失败并跳过自动发布；若最终没有入选条目，则报错，不把网络故障写成正常的 `.no-content`，也不覆盖已有当日文件。发布阶段耗尽时，本地简报仍保留。日志以 `component=network_recovery` 标明等待、恢复和额度耗尽，不输出请求地址、正文或凭据。

额度约束累计长等待，不是整次运行的硬超时；正常请求和处理另计。普通单站故障不会将运行标记为全局恢复耗尽，也不因此阻止其他内容发布。恢复仅限进程存活期间，不持久化执行进度，不支持进程重启后从中间恢复。

## 模型服务

生成、重试和模型回放统一通过 `LLM_PROVIDER` 选择接口，未设置时保留 Gemini；设为 `openrouter` 时，默认用 Qwen3.8 Flash 分类（关闭思考）、GPT-6 Luna 生成摘要及当天判重（medium 思考）。普通材料与社区汇总仍走各自的既有输入和输出契约，OpenRouter 不隐式回退到 Gemini 或其他模型。

模型配置使用 `OPENROUTER_`、`GEMINI_` 前缀，发布使用 `PUBLISH_URL` 和 `PUBLISH_TOKEN`；原有 `DAILY_BRIEF_` 环境变量不再读取。模板只列出常用设置，费用保护继续使用代码默认值，不常用的覆盖项见 [LLM 模块的高级配置说明](../src/daily_brief/llm/README.md#advanced-configuration)。

OpenRouter 请求使用严格 JSON schema，并限制供应商单价、输出量、响应大小、请求间隔和重试次数。临时服务错误、限流或网络失败可有限重试；鉴权、余额不足、地区限制、格式错误和材料不足不重复请求。每个 backend 实例在调用前预留成本，收到明确费用后更新，未知费用的失败保留预留；默认每次运行上限 $0.25，不是跨进程或月度账单上限。分类、摘要和当天判重共享该额度，调用费用写入日志；摘要 token 诊断沿用候选记录，公开简报字段不变。

摘要在简洁之外保留解释结果的具体做法及数字口径，不以最短篇幅作为目标。OpenRouter 的网络出口独立于模型选择配置；本机使用精确域名规则时须实际验证模型请求，公共连通性检查不保证地区资格。

## 当天内容去重与补选

候选收集阶段的精确去重仍按相同 HN ID 或完全相同的原始网址合并；历史去重仍只屏蔽过去七天入选的 HN ID，不比较跨日内容。

新增的内容比较位于摘要完成后、写出文件前，覆盖两个栏目。首次比较先放技术精选，再放圈外热门，各栏目保持原排名。只纳入摘要成功且非空的条目；失败摘要保留既有展示方式，不因材料不足被判断为重复。不足两个可比较条目时不调用模型。

OpenRouter 判重复用 `OPENROUTER_SUMMARIZER_MODEL`（默认 GPT-6 Luna）、摘要单价上限及请求间隔，请求 medium 思考，思考与最终答案合计最多 8,192 token；修改摘要模型配置也会改变判重模型。费用仍计入实例共享预算，判重模型、请求思考强度及实际 token 用量独立记录，不覆盖摘要诊断。Gemini 继续使用分类模型，输出上限为 2,048 token。输出截断视为调用失败，保留当前内容。

每条输入包含标题、摘要和最多 4,000 字符的证据；网页正文优先，帖子正文和评论单独标记。社区汇总优先提供评论证据，问题仅作上下文。提示词使用通用的信息覆盖、解释深度、限定条件和证据支持标准，不包含已知评测案例的答案。判重需要材料支持相同对象和核心事实，不能从模糊摘要或缺少差异推断重复。篇幅长或排序靠前本身不代表信息更充分；一篇覆盖核心信息、另一篇提供独立增量时可以同时保留。完全被覆盖的简短版本不能仅因受众、形式或阅读成本不同而占据独立名额。

模型输出每条的保留或重复决定、重复对象及简短理由。重复对象可以位于输入的任意位置，但必须在同一批结果中保留，且直接覆盖被剔除条目的核心信息。程序先校验整批覆盖和字段，再基于完整结果校验引用；自引用、未知 ID、循环和指向其他重复条目的链都会导致整批失败，不应用任何删除。事件相同或通过第三篇产生的相似关系不构成重复依据。

被剔除条目记录 `rejection_reason=content_duplicate`。补选只使用已通过原有资格要求的候选，技术栏目按分数、圈外栏目按积分和评论排名，不重跑分类；社区汇总已成功生成的摘要直接复用。补选后仍将当前全部可用条目交给模型，但程序只采用涉及本轮新补选条目的重复判断：新条目可以因旧条目或同轮其他新条目覆盖而删除，也可以替换信息较少的旧条目。旧条目之间的改判不执行，前一轮已保留的补选条目在下一轮也视为旧条目。程序先验证整批响应，再过滤旧条目之间的删除，不能用过滤绕过循环、链等结构校验。删除后的空位仍由其原栏目补选。被删除的候选不会重新进入待选队列。最多处理 `CONTENT_DEDUP_MAX_REPLACEMENTS=3` 个补选候选，因此最多四轮内容比较；候选耗尽或达到上限时允许少于栏目名额。最终历史只记录留下的条目。

输入材料不确定时保留；调用失败、预算不足或结构化结果无效时保留当前内容并停止追加补选。该可选检查仅使用模型短重试，不消耗定时运行的十分钟网络暂停额度。`retry` 仍只刷新指定条目的材料和摘要，不重新判重或补选。

私有候选记录的 `content_deduplication` 数组记录每一轮参与比较时的状态（`retained`、`duplicate`、`failed`、`skipped`）、重复对象、理由、模型及错误类型。旧条目之间被忽略的删除判断记录为 `retained`、空重复对象及 `reason=old_to_old_duplicate_ignored`，如实反映程序实际保留的结果。某条可以先保留、后被更完整的补选条目替换；引用表示当轮的直接判断，不改写此前的记录。最终是否入选以 `selected` 为准。日志 `component=content_deduplication` 记录比较数量、剔除数量及耗时，OpenRouter 的 `task=deduplicate` 记录 token 和费用。原文和完整模型输入不会因判重写入正常产物，公开 JSON schema 不变。

判重模型的可复现实验见 [`evals/content_deduplication/`](../evals/content_deduplication/README.md)。已知案例的回归检查与独立合成案例分别报告；每个案例按不同输入顺序重复运行，检查保留集合、引用及稳定性。真实模型实验与不调用外部服务的程序测试分开执行。

## 原文获取

获取原文时，系统会根据链接类型，选择对应的读取方式：

- **普通网页**：下载页面，提取正文，去除导航、广告等无关内容。系统不会像浏览器一样执行 JavaScript，因此有些网页虽然能手动打开，也可能提取不到正文。
- **GitHub**：仓库链接读取 README；指向具体文件的链接读取该文件；`/owner/repo/issues/编号` 链接优先通过公开 REST API 读取 issue 描述。
- **YouTube**：获取视频字幕，作为摘要依据。
- **PDF**：下载文件后提取文字。配置了 Adobe 服务时优先使用 Adobe；未配置或转换失败时，使用本地的 `pypdf`。

普通入选条目的摘要材料由下列相互独立的分区组成：

- **网页元信息**：来源页面对自身内容或产品的简短说明；用于补充对象定位，不能把发布者的宣传或自评当作独立验证的结论。
- **网页正文**：提取出的文章、页面、README、字幕或 PDF 文字。
- **HN 帖子正文**：提交到 HN 时附带的文字；它是发帖者提供的介绍，不必然代表项目作者。
- **HN 评论样本**：有界取得的部分讨论，可提供经验、限制、质疑或纠错，但不代表整个社区的共识。

网页正文、帖子正文和评论不会互相覆盖；某一分区为空或获取失败时，其他可用分区仍会继续进入摘要。模型根据全部已提供材料判断是否能写出可靠摘要，因此“没有摘要”可能是全部材料都不可用，也可能是这些材料合在一起仍不足。评论的噪声或重复内容可以不写入摘要。

以下恢复流程用于已入选的条目。筛选阶段需要读取原文时，只采用较有限的获取方式，不启用 Jina、Wayback 或搜索恢复；已成功取得的正文会在入选后复用。

### 普通网页获取失败后怎么办

对于已经入选的条目，系统默认尝试备用获取通道，少数明确的错误采用例外处理；不再要求识别出特定的反爬服务。任何一步取得正文后，就停止这条恢复流程。

直连 HTML、Jina Reader 和 Wayback 的 HTML 共用空壳检查：在大小校验通过后，若正文只剩已识别的启用 JavaScript 提示、常见导航或地区／语言选择控件，则按 `empty_content` 继续恢复。网页标题和介绍不能代替正文；检查 Markdown 时保留链接文字、忽略图片及链接格式。明确 JS 提示旁重复的站点标题可忽略，但带句末标点或数字的标题、未知正文和控件仍保留，避免误伤短公告。这是有限规则的空壳识别，不是语义充分性判断，不设正文最低字数，也不改写通过检查的材料。Reader 返回空壳会继续尝试存档；存档仍无正文时可继续搜索。分类阶段仍遵守不启用备用渠道的既有策略。

有一种限定的链接纠错例外：原地址（不是重定向后的地址）返回 HTTP 404，且路径以字面反斜杠 `\` 结尾时，删除最后一个反斜杠，再直接请求一次。查询参数与片段保持原样，不修改百分号编码的字符，也不猜测其他路径。修正地址重新通过公网地址校验，使用相同的下载和提取限制；若仍失败，就结束网页获取，不追加超时重试、Jina、存档或搜索恢复。筛选阶段不启用这一纠错。

纠错不改原始 `source_url`；成功后的实际地址保存在 `retrieved_url`，尝试次数包含原请求和纠错请求。私有诊断与日志以 `url_trailing_backslash` 记录纠错原因，失败时保留最后的错误。公开详情的获取方式仍是直接请求，纠错原因映射为既有的 `unknown`，不增加公开 schema 枚举。

1. **短暂故障先有限重试，明确的终止错误不重复请求。**\
   网络超时、连接中断、HTTP 408 和普通 5xx 最多直接重试一次。普通 HTTP 429 也最多重试一次，仍限流就结束该地址获取，不立即转用 Jina。`Retry-After` 支持秒数和 HTTP 日期；缺失或无效时等待一秒，有效等待超过 15 秒或无法放入剩余预算时，跳过直连重试，不缩短服务端要求的等待。408、5xx 仍可转用 Jina，429 则结束该地址获取。只有实际再次直连时才等待。401、407 认证错误，400、422 请求错误及 451 不启动普通恢复。

   明确识别到的验证响应直接进入恢复，不因使用 5xx 状态而先重试直连；保留原诊断，包括 DataDome 的 401、Vercel 的 429。但 429 同时提供 `Retry-After` 时优先按限流处理。其他证书校验错误、非公网地址、下载或解析硬限制、URL 纠错后的失败保留终止行为。

2. **默认尝试 Jina Reader，404/410 直接转存档。**\
   Jina Reader 是代为读取网页、返回正文的服务。普通 403 和其他未被上述例外排除的 HTTP 错误，均可尝试 Jina，无需反爬响应头。正文提取为空、重试后的网络故障及缺少证书签发者信息也进入此路径。404、410 跳过 Jina，直接查找原页面存档；限定的反斜杠 URL 纠错仍先执行。

   Reader 接口成功与原站状态分别校验：成功的 JSON 响应中，原站状态允许 2xx，以及可能伴随已渲染正文的 301、302、303、307、308；其他状态（包括 304）、缺失或格式异常仍拒绝。允许的状态还必须通过公网 URL、正文非空、验证页识别和大小校验，不能仅凭状态判断正文可用或完整。成功后停止恢复流程，保留原请求参数。每次 Reader 请求在日志中记录外层 HTTP 状态、JSON code/status、原站状态和正文字符数，不记录正文或凭据；状态校验失败的错误信息包含实际数字状态，异常类型的值只记录标记。

   Reader 的发布时间优先读取 `publishedTime`；缺失、非字符串、空白或超过 64 字符时，回退到 `metadata.article:published_time`。该信息传入材料来源证据，供同事件报道日期核验使用；不使用修改时间代替发布时间。

3. **Jina 未取得正文时，尝试网页存档。**\
   系统会到 Wayback Machine 查找该页面的历史存档，确认来源与时间符合要求后提取正文。此步骤同样适用于普通 HTTP 错误、超时、连接失败或正文为空；不安全 URL 和预算耗尽会立即停止，不继续恢复。

4. **如果原站仍未取得正文，再搜索其他来源。**\
   系统会尝试寻找同一篇文章的其他发布页面；特定情况下，还会寻找 Reuters 的转载或其他媒体的同事件报道。这部分有单独的验证规则，下一段展开。

GitHub issue 在分类和摘要阶段均优先请求 `/repos/{owner}/{repo}/issues/{number}`，读取并核对返回的仓库、issue 编号及页面地址。标题单独作为元信息，非空 Markdown `body` 作为正文，保留代码块；不获取 issue 评论，不把 PR、issue 列表或其他 GitHub 页面当成 issue。发布时间使用 API 的 `created_at`，不用更新时间。查询参数和页面锚点不改变目标 issue。

仓库改名或 issue 转移时，允许跟随 GitHub API 的重定向，直接使用新资源的正文。每一跳仍须通过公网地址校验，并限定为 HTTPS、精确的 `api.github.com` 主机及 issue API 路径；支持 `/repos/{owner}/{repo}/issues/{number}` 和 `/repositories/{id}/issues/{number}`。校验依据是最终 API 地址、响应的 `url`、`html_url` 和 `number`：允许仓库和编号随官方重定向变化，数字仓库路径的名称由可信响应中相互一致的 API／网页地址确定。未重定向时仍按原资源核对；外域中转、HTTP 降级及身份冲突均拒绝。原 `source_url` 保留，`retrieved_url` 记录新网页地址；正常迁移仍是 API 直接获取成功，不记为 fallback。

issue API 与普通网页共用短重试、大小限制及获取预算。摘要阶段遇到空正文或可恢复的网络错误时，针对原 issue 页面地址尝试 Jina、Wayback 及既有搜索恢复；API 的 404/410 直接转存档，不再用普通 HTML 提取器重复读取已知容易漏正文的页面。分类阶段仍不启用这些备用渠道。API 配额耗尽（429，或带 `X-RateLimit-Remaining: 0`／`Retry-After` 的 403）停止 API 重试，摘要阶段立即对原 issue 页面进入 Jina、Wayback 及适用的搜索恢复，私有原因记录为 `github_api_rate_limited`，公开 `generation_info` 映射为既有的 `rate_limited`。分类阶段只记录失败，不启动恢复。没有限流证据的 API 403 权限错误、其他终止类 HTTP 错误、无效响应或身份不符、非公网地址及大小限制不会转入恢复。私有诊断记录 `method=github_issue`、`extractor=github_api`；公开详情将该方式映射为既有的 `direct`，表示直接请求原站 API，不增加网站 schema 枚举。

GitHub README、具体文件和 YouTube 使用各自的读取方式，失败后仍不会进入 Jina 和 Wayback 的恢复流程。

GitHub issue 和 README 的 REST API 请求读取可选环境变量 `GITHUB_TOKEN`；未配置或留空时匿名请求，配置后在首次 `https://api.github.com/repos/...` 请求上添加 Bearer 认证。凭据使用不随重定向自动转发的请求头；仅 issue API 重定向在每一跳通过公网地址与 issue 接口校验后重新附加 token，使迁移后的请求继续使用认证配额。README 重定向、raw 文件下载、普通网页及 Jina／存档等备用渠道均不携带此 token。认证不改变既有重试和恢复条件；token 中存在非法请求头字符时在本地失败，错误信息不包含凭据。

普通网页获取与后续搜索共用每条 120 秒、24 次传输请求的预算，包含直接重试、Jina 匿名/带 key 请求、存档索引与回放、Tavily 搜索及候选页面获取；嵌套调用不会重置预算。GitHub 候选的 HTTP 请求也计入。预算决定是否开始下一次请求或恢复阶段，socket timeout 不超过剩余时间；已经返回的结果继续通过正常内容校验，不因完成时超过 120 秒而丢弃。PDF 转换不受该期限中止，Adobe 在分类和摘要阶段均保留原有 300 秒转换上限；PDF 和 YouTube 的其他子进程限制也保持独立。urllib 内部重定向不逐跳计数，仍受既有重定向和公网校验限制。无可用结果且预算耗尽时停止追加获取并记录 `retrieval_budget_exhausted`，HN 材料和摘要调用仍可继续。

普通 HTTP 回退原因在私有诊断中保留为 `http_403` 等具体状态码；公开 `generation_info` 沿用 `http_error`，连接失败 `request_failed` 映射为既有 `network_error`。预算耗尽仍在私有诊断保留具体原因，公开映射为 `unknown`，不发布原始错误。

### 如何搜索其他来源

已入选的普通网页在适用的 Jina、Wayback 路径耗尽后，系统会尝试搜索其他来源。触发原因包括普通 HTTP 错误、404/410、验证页、正文为空、网络故障及 GitHub issue API 配额耗尽；认证或请求错误、普通网站限流、恢复渠道最终限流、不安全地址、URL 纠错终止、专用 transport 失败和预算耗尽不触发搜索。搜索使用 Tavily，需要配置 `TAVILY_API_KEY`。

**先找同一篇文章的其他发布页面。**\
系统用文章标题搜索，再实际打开候选页面。页面需要有标题、明确的转载说明和指向原文的链接，以及可用的正文，才会被接受。标题可以与 HN 标题不同；转载身份由明确指向原文的来源关系确认。仅仅搜索结果看起来相似，并不足以采用。

**如果没找到，再根据原链接决定下一步：**

- **原链接来自 Reuters**：先尝试寻找经过验证的 Reuters 转载，不再要求原站错误必须来自 DataDome；未取得可用转载且预算仍允许时，继续同事件报道恢复。
- **同事件报道恢复**：原链接来自其他网站时直接进入此步骤；Reuters 则在转载恢复失败后进入。先核验同稿搜索中已读取但未被认定为同稿的页面；没有可用材料时，再搜索其他媒体对同一事件的报道，不限定 Reuters。采用后，详情中的材料来源记录为其他报道，原链接保持不变。

任何一步取得可用材料后停止恢复。诊断保留已执行的同稿、Reuters 转载和同事件报道结果，以及原站失败原因；预算耗尽时不启动下一阶段。

同事件报道需要有实质正文、接近原文日期（原链接没有日期时用 HN 提交日期，允许相差两天）的报道日期，以及正文中的事件关键词、可识别的人物或机构名称和关键金额、比例等信息。标题不要求相同，搜索结果的标题和片段不作为核验材料。明确的网页发布时间优先于正文日期；页面提取器读取发布时间元信息、文章结构化数据和文章页头的时间标记，不用修改日期代替。无法确认日期或事件一致性时不采用。此核验基于文本规则，不能替代事实核查。

同事件路径跳过已知的社交、讨论和代码托管站点；候选及重定向仍须通过公网地址校验。每次最多核验五个页面，包含上一步已取得的材料，复用不产生重复请求；必要时最多追加一次搜索。多份通过核验的材料若日期或事件关键词明显不一致，就放弃该路径，否则选正文最长的一份。摘要提示明确材料来自其他报道，并要求对指控、争议及未经证实的主张保留归因。

每条搜索路径都有尝试次数限制。找到的页面如果无法获取或未通过验证，就继续检查下一个候选；不会因此启动新一轮搜索。即使最终没有外部正文，HN 帖子正文和评论材料仍可供摘要调用使用。

### HN 评论材料

每个普通入选条目都会在摘要调用前读取一份有界 HN 评论样本，不再以网页正文是否足够作为是否读取评论的条件。评论获取只尝试一次；失败或空结果不会阻止使用网页材料和帖子正文，也不会触发第二次语义回退摘要调用。

采样按广度优先遍历，先读取顶层评论，再读取回复；没有独立的有效评论条数上限。每份样本最多读取 40 个条目（含帖子本身），总材料最多 16,000 字符（含标签和分隔符），单条正文最多 2,000 字符，回复最深到第 3 层。失败、已删除、隐藏或空评论仍消耗条目读取额度，因此默认最多取得 39 条评论。读取异常或无效条目累计达到 3 次时停止，保留已取得的材料。回复只在父评论完整进入样本后才会读取，避免缺失上下文；单条截断不会阻止继续读取其他线程。

私有 `discussion_retrieval` 和采样日志记录已纳入的顶层评论数 `top_level_comments`、回复数 `reply_comments` 及停止原因 `stop_reason`。原因分别为 `request_limit`（读取额度）、`char_limit`（总字符额度）、`failure_limit`（失败阈值）、`queue_exhausted`（没有剩余可读节点）。最后一条正文因总字符额度截断或放不下时仍记为 `char_limit`；第三次失败即使恰好用完请求额度也记为 `failure_limit`。正常处理完后，队列为空优先记为 `queue_exhausted`；尚有节点时先检查字符、再检查请求额度。队列耗尽只表示深度和父上下文限制下没有剩余节点，不代表完整读取了整个讨论。未尝试或获取失败时计数为零、停止原因为空；这些字段不进入公开简报。部分有效材料仍可交给摘要模型，停止原因不等同于摘要失败。

摘要输入仍将四类材料分开标记，输出是一条按内容组织的完整摘要，不再分别汇报来源或附加评论概览。提示要求先讲清对象、变化或观点，再保留关键机制、结果和限制，去掉重复、空泛评价及无关轶事。通常两到四句，按内容复杂程度调整，没有最低字数要求；解析器保留 1,000 字符的防御性上限。

提示用标题定位事件、用材料核实，并优先保留有区分度的主体、方法和贡献；影响核心主体识别的名称、型号或版本不能被泛称替代。网页元信息可以补充正文泛称对应的身份，冲突时以正文为准；采用这些细节也须在 `summary_sources` 中申报元信息来源，不能只报告占主要篇幅的来源。

提示将核心解释及其限制放在案例之前，并要求在对应说法旁保留功能状态（已可用、预览、计划）、作者预期与实验观察的区别、指标口径及测量范围。材料没有确认的信息不能推断补齐；必要时收窄表述或省略可能误导的细节。这些是生成指令，响应校验器不做语义核验。

评论只有提供具体增量时才进入摘要，有用细节放在所解释的对象或结论旁，不在结尾追加评论说明；个人经验、作者观点和有争议的说法在相关句子中自然归因，不能写成已经证实的事实或社区共识。模型可省略所有评论；只有评论可用时也可据此概括实质观点和分歧。普通自发帖若在征集推荐或经验，摘要直接从具体回答写起，保留推荐内容及评价方向，不复述提问、逐项重复推荐者或只列名称。

模型返回 `status`、`summary`、`summary_sources` 和 `reason`。程序检查来源数组没有重复、未知或不可用来源，以及充分性决定与字段内容是否一致。`summary_sources` 写入私有 `summary_sources_used`，用于生成公开来源详情；这是模型声明的使用情况，不是逐句事实核验。程序不再添加“根据网页内容”“根据 Hacker News 部分评论”等固定前缀。历史输入回放的 legacy 路径仍保留旧输出契约。

摘要的充分性判断针对这一次调用中实际提供的全部材料。

征集工具、项目或经验的帖子仍是例外：这类 `community_roundup` 的评论在筛选阶段承担判断内容价值的职责，成功概览会在入选后复用，保留列表格式，通过诊断和公开详情记录评论来源，不添加固定前缀。

### 摘要的时间语境

所有摘要路线都显式接收简报日期、HN 提交时间和已取得网页的发布日期。简报日期采用本次简报标签，历史 retry 采用目标简报日期，模型回放采用保存的日期，不随执行当天变化。HN 提交时间只表示分享时间，不代替原文或事件日期；转载、其他报道的发布日期属于实际取得的页面。获取阶段已有的发布时间信息在材料复用时保留；缺失、不支持或无效的日期在提示中标为未知，只有通过 ISO 日期或时间戳解析的值进入时间字段。

提示要求按来源语境理解“今天、明年、即将”，优先保留明确日期，区分计划与已确认的结果。预定日期已过不能证明计划已实现，旧文使用“将于”也不能证明当前尚未发生。页面新旧表述并存时结合日期和状态证据判断，无法确认则保留计划及归因或省略无依据的当前状态。历史重试可能取得较新的页面，不能将后续状态写成简报当时已知的事实。这些是生成约束，不是响应校验器提供的语义保证。

时间字段保存在私有候选诊断和 schema 7 模型输入捕获中，不增加公开简报字段。旧版 schema 3–6 输入回放以顶层简报日期补充参考日期，网页发布日期仍为未知。

## 重新获取材料并生成摘要

使用 `daily-brief retry --date YYYY-MM-DD` 可以重试已有简报中摘要失败、材料不足，或网页/评论获取失败的入选条目。若上次重试未取得 HN 帖子正文，也会再次尝试。指定 `--item HN_ID` 则只重做该入选条目，即使原摘要已成功；可重复指定多个 `--item`。

命令读取同一天的公开简报 JSON 和候选诊断，先验证日期、条目和栏目一致，再重新请求 HN 帖子正文、原链接网页和评论。原来的入选集合、顺序、标题、链接、热度数据和推荐理由保持不变，不重新收集候选或筛选。普通条目复用四材料摘要流程；征集帖复用评论资格判断和列表摘要。历史日期决定存档获取的时间界限，实时页面和评论则反映本次请求时的内容。

摘要成功才更新对应条目的公开 JSON 结果和诊断。失败时保留旧结果，将最近一次尝试的状态和错误写入候选诊断的 `last_retry`；下次重试覆盖这一记录，不累计保存正文、评论或模型输入。网页或评论中的某个来源失败，不会阻止使用其余可用材料生成摘要。

写入前会检查文件是否在重试期间被修改，避免覆盖并发的生成或手动编辑。各文件采用原子替换，普通写入错误会回滚已替换文件，但不保证进程崩溃时的跨文件事务。重试不改推荐历史、不自动发布；确认本地结果后，仍使用 `daily-brief publish --date YYYY-MM-DD` 发布。没有待重试条目时不改文件；只要有目标条目未生成成功，命令就返回非零退出码。

## 如何定位原文获取问题

### 第一步：找到当天的条目

打开 `data/YYYY-MM-DD-hn-candidates.json`，按标题、原文链接（`source_url`）或 HN 条目编号（`hn_item_id`）找到对应记录。完整诊断保存在候选记录中；公开简报 JSON 通过 `generation_info` 提供经过白名单转换的生成信息，供网站折叠展示。它分开记录网页、HN 帖子、HN 评论的获取状态、模型声明使用的材料，以及摘要生成状态和实际调用模型。不发布原始错误、恢复 URL 或搜索候选记录。旧的公开条目字段 `provenance` 已移除，生成器不再输出，校验器也不再接受。

网页获取方式表示最终记录的尝试方式，失败时不能当作成功路径；其他来源恢复成功时，原因优先保留原站失败的原因。摘要采用的来源由 `summary_sources` 表示，不从 `content_status` 或“已取得评论”推断。这是模型声明，不是逐句事实核验，详情也不是完整的重试时间线。

`generation_info` 仍是 schema v2 的可选字段；生成器为每条输出它，校验器也接受缺少它的条目，不补写推测值。材料获取状态区分成功、空内容、失败、未尝试、不需要和未知；成功取得评论但未达到征集帖资格门槛时，仍表示获取成功。HN 帖子在候选收集和 retry 中显式记录状态，fresh story 请求失败不会伪装为空帖子。摘要材料列表来自模型声明的 `summary_sources_used`，不是输入材料清单，也不是事实核验；成功摘要缺少声明时为 null，未生成摘要时为 []。模型标识仅允许长度不超过 128 的 ASCII 标识符，未记录时为 null。`generation.reasoning_effort` 为可选字段，仅从本次摘要调用记录导出请求的思考强度（`none`、`minimal`、`low`、`medium`、`high`、`xhigh`，也接受 null）；OpenRouter 请求和诊断共用固定 medium 配置。这不是实际思考 token 用量。历史条目或未记录该配置的后端不补写字段，请求前预算耗尽也不会沿用上次调用的值。接收端须先支持该字段，再发布含有它的新简报。公开失败原因只使用确定的枚举投影，不发布原始异常或模型生成的理由。失败 retry 保留旧摘要及其生成信息，最新失败仍在私有 `last_retry`。

先看 `selected`：如果没有入选，查看 `rejection_reason` 了解原因。条目可能在筛选阶段就被排除，因此没有执行后续的获取和恢复流程。

### 第二步：判断问题发生在哪里

按下面几个字段区分情况：

- **`article_retrieval.status` 为 `failed`**：没有取得可用的外部正文，继续查看第三步中的抓取和恢复记录。`not_attempted` 则表示没有尝试抓取，不代表抓取失败。
- **`source_material.status` 为 `insufficient`**：没有可用材料，或模型判断汇集的材料仍不足；具体原因在同一组字段的 `reason` 中。
- **`summary_generation.status` 为 `failed`**：摘要生成出错，查看同一组字段的 `error_code` 和 `error_message`，定位模型调用或输出处理问题。

这些情况可能同时出现。例如，网页获取失败后，帖子正文和评论仍可能支持摘要。用 `summary_status` 查看最终结果，`summary_sources_used` 查看实际使用的材料来源；不要只凭原文抓取状态或评论取得状态判断是否有摘要或实际采用了评论。

### 第三步：查看对应的尝试记录

**如果是抓取失败**，查看 `article_retrieval` 中的 `method`、`error_code` 和 `error_message`，确认获取方式和具体错误；`fallback_reason` 说明为什么触发了回退。

例如，`method=wayback`、`fallback_reason=cloudflare_challenge` 表示原站遇到 Cloudflare 人机验证，恢复流程已经尝试到 Wayback。此时 `error_code` 解释存档获取为何失败；是否继续搜索其他来源，要看下面的搜索记录。

Wayback 在允许时间范围内未找到符合条件的存档时，私有错误码为 `wayback_no_capture`，公开 `generation_info` 映射为 `archive_unavailable`，网站显示“未找到可用存档”。这一公开原因需要网站接收端先支持，再发布使用它的简报；历史 `unknown` 不自动补写。

Jina 的一般请求失败仍记为 `request_failed`，私有错误信息和 `component=jina_reader event=request_failure` 日志额外保留异常类型；`URLError` 包装的异常还记录 `reason_type`，用于区分超时和 DNS 等故障。诊断不复制异常文本或字符串形式的 reason，避免输出 URL 或凭据；类型信息会保留到后续 Wayback 组合失败中，不改变获取和重试策略。

**如果需要了解搜索恢复**，查看 `article_retrieval` 中对应的记录：

- `same_article_recovery`：寻找同一篇文章，`candidates` 中记录每个候选的结果和原因。
- `syndicated_recovery`：寻找 Reuters 转载，查看 `status`、`error_code` 和 `rejection_reasons`。
- `alternate_reporting_recovery`：寻找同事件报道，查看相同的三个字段。

搜索恢复成功时，`material_origin` 和 `retrieved_url` 记录实际取得的来源，原站失败信息保留在 `origin_failure` 中。

**如果需要查看 HN 评论材料**，查看 `discussion_retrieval.status`；获取出错时看其中的 `error_code` 和 `error_message`。它记录评论样本是否可用，不等同于评论被摘要采用。各材料的实际使用结果保存在私有候选审计中；最终摘要生成结果则看 `summary_generation`。

需要还原完整尝试顺序时，再结合运行日志查看。抓取日志标有 `component=article_fetch`，PDF 提取标有 `component=pdf_extract`，搜索恢复的标记与上面的三个记录名称相同。
