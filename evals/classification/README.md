# 分类评测集

这 50 条历史案例用于比较模型的分类表现，每类 10 条。它们检查内容属于哪个领域，以及是否需要按社区征集帖处理；不评估最终选哪些条目，也不评估摘要质量。

## 五种分类

| 标签 | 含义 |
| --- | --- |
| `ai` | AI 是主要内容、核心方法或关键影响因素。 |
| `core_non_ai` | 主要内容属于计算机或软件领域，AI 不是核心。 |
| `outside` | 材料明确表明主题在计算机和软件领域之外。 |
| `uncertain` | 现有材料不足以支持明确分类。 |
| `community_roundup` | HN 自发帖征集项目、推荐或实践经验，主要价值在回答中。 |

详细规则见[分类提示词](../../src/daily_brief/llm/topic_classifier.py)。按当前规则，标题可以帮助理解材料，但不能单独作为主题判断依据。

## 案例文件

[`cases.json`](./cases.json) 保存测试输入和预期答案：

- `id`：HN 条目 ID。
- `input`：交给分类模型的标题、来源域名、自发帖标记和正文节选。材料已经保存在文件里，不需要重新抓取网页。
- `expected_label`、`reason_zh`：预期分类，以及中文判断理由。
- `source`：原始链接、发帖时间和本地历史记录的位置。本地路径和记录位置只用于追溯来源，运行评测不依赖这些历史文件。

材料来自 17 条历史分类输入、9 条复用的摘要输入，以及 24 条历史自发帖。它们经过项目现有的提示词构造逻辑，整理成首次分类时使用的输入；较长正文会被截取，因此不一定是完整原文，也不保证与历史运行时的提示词完全相同。

初选后经过另一个 agent 独立复核，50 条分类判断一致。它们作为第一版预期答案，后续仍可纠正。

## 怎么使用

用项目的分类指令配合每条 `input` 进行评测。比较不同模型时，保持输入材料和指令一致。只把 `input` 作为案例材料交给模型，不提供预期答案、判断理由或来源记录。

将模型输出与 `expected_label` 对照，分别统计各类结果。出现分歧时，先看具体材料和判断理由，再决定是模型出错，还是预期答案需要修改。

目前这里只保存数据，还没有评测脚本。它与现有 `daily-brief evaluate-model` 命令使用的输入格式不同，不能直接交给该命令运行。

## 目前的不足

- 每类数量相同，是为了检查不同类型的表现。总通过率不代表日常运行的准确率。
- `uncertain` 主要覆盖材料不足，还没有充分覆盖其他模糊情况。
- `community_roundup` 只检查是否识别为征集帖，没有覆盖获取评论后再次判断主题的步骤。

以后遇到新的问题或分类规则变化，再补充或修改案例，并在 Git 提交中说明原因。
